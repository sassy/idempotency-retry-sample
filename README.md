# idempotency-retry-sample

冪等性（Idempotency）とリトライを、動くコードで検証するための小さなサンプルです。Rust + axum で書いています。

## これは何か（正直な前提）

このコードは実務のプロダクトから切り出したものではありません。設計・アーキテクチャの学習の中で「冪等性とリトライを自分の実務で活かせる場面が見つからない」という壁にぶつかり、**実務事例がないなら、壊れる条件をコードで再現して確かめればいい**と考えて作った検証用サンプルです。

- 「キーなしだと本当に二重課金が起きるのか」
- 「同じキーでリトライすれば、本当に1回しか課金されないのか」
- 「キーが別々に作られてしまったら、何が最後の砦になるのか」

を、自動テストで再現・確認できる形にしています。

## 題材：支払いAPI

```
POST /orders/{order_id}/payments
Idempotency-Key: <支払いの試行ごとに作るキー>
Content-Type: application/json

{"amount": 1000, "currency": "JPY"}
```

「その処理が2回起きたら、誰かのお金・在庫・権利が変わるか」が冪等性を考える場面の見分け方で、支払いはその代表例です。

## 2層の防御

| 層 | 仕組み | 防ぐもの |
|---|---|---|
| 第1層：試行単位の冪等キー | `Idempotency-Key` と処理結果を保存し、同じキーの再送には保存したレスポンスを返す | 二重クリック、タイムアウト後のリトライ、応答ロスト |
| 第2層：注文単位の一意性 | 注文ごとに成功した支払いは1件だけ（本番では部分ユニークインデックス） | 別タブなどで**別のキー**が作られてしまったケース |

第1層だけでは「キーが変わってしまう」ケースを防げません。逆に第2層だけでは、リトライのたびにエラーが返り、クライアントは「成功したのか失敗したのか」が分からなくなります。だから2層を重ねます。

キーの作り方がポイントです。**リクエストごとではなく、支払いの試行ごとに1つ**作ります。クリックのたびに新しいキーを作ると、第1層はまったく効きません。

## 検証シナリオ（自動テスト）

`tests/api.rs` で次の4場面を再現しています。

| # | 場面 | 期待結果 |
|---|---|---|
| 1 | キーなしで同じ支払いを2回送信 | **課金が2件（二重課金の再現）** |
| 2 | 同じキーでリトライ（1回目の応答がロストした想定で、レスポンスを捨てて再送） | 課金は1件、2回のレスポンスは完全に同一 |
| 3 | 同じキーのリクエストを並行送信 | 課金は1件。もう一方は結果の再生か 409 `request_in_progress` のどちらか |
| 4 | 支払い済みの注文に、別のキーで支払い | 409 `order_already_paid` で拒否、課金は1件 |

そのほか、同じキーを違う金額で再利用した場合の 422 `idempotency_key_reused_with_different_payload` もテストしています。

### レスポンスの規則

| 状況 | ステータス | コード |
|---|---|---|
| 支払い成功（初回） | 201 | — |
| 同じキー・同じ内容（完了済み） | 201（保存したレスポンスを再生） | — |
| 同じキー・同じ内容（処理中） | 409 | `request_in_progress`（`Retry-After: 1` 付き） |
| 同じキー・違う内容 | 422 | `idempotency_key_reused_with_different_payload` |
| 別のキー・支払い済みの注文 | 409 | `order_already_paid` |
| キーなし | 201（無防備に処理） | — ※場面1の再現用 |

## 動かし方

外部DBやサービスは不要です。

```bash
cargo test   # テスト（シナリオ1〜4 + リトライの単体テスト）
cargo run    # サーバー起動（http://127.0.0.1:3000）
```

curl の例：

```bash
# 初回：成功（201、pay_1）
curl -i -X POST http://127.0.0.1:3000/orders/order_1/payments \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: attempt_1' \
  -d '{"amount": 1000, "currency": "JPY"}'

# 同じキーで再送：保存されたレスポンスがそのまま返る（課金は増えない）
curl -i -X POST http://127.0.0.1:3000/orders/order_1/payments \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: attempt_1' \
  -d '{"amount": 1000, "currency": "JPY"}'

# 別のキーで再送：409 order_already_paid
curl -i -X POST http://127.0.0.1:3000/orders/order_1/payments \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: attempt_2' \
  -d '{"amount": 1000, "currency": "JPY"}'

# キーなし（危険な経路）：送るたびに新しい支払いができる
curl -i -X POST http://127.0.0.1:3000/orders/order_2/payments \
  -H 'Content-Type: application/json' \
  -d '{"amount": 1000, "currency": "JPY"}'
```

## 実装メモ：インメモリ → PostgreSQL への対応

サンプルでは学習のために、状態をインメモリの `Store`（`src/store.rs`）に置き、単一のロックで「チェックと登録を不可分にする」ことを表現しています。本番相当のDDLは `schema.postgres.sql` にあります。

| サンプルの実装 | 本番（PostgreSQL） |
|---|---|
| `Store.idempotency_keys`（HashMap） | `idempotency_keys` テーブル（主キー：注文ID＋キー） |
| ロックを取ってキー有無を確認し `processing` で登録 | `INSERT ... ON CONFLICT DO NOTHING` でキーを確保（取れた者だけが処理する） |
| `Store.payments` + `order_already_paid()` チェック | `payments` テーブルの**部分ユニークインデックス**（`WHERE status = 'succeeded'`） |
| `charge_count` | 決済ゲートウェイへの実際の呼び出し回数 |

## クライアント側のリトライ方針（`src/retry.rs`）

送る側は、やみくもに再送せず次の方針にします。

- **再送するのは冪等なリクエストだけ**（＝冪等キーを付けたリクエストだけ）
- 再送するのは **タイムアウトと5xx** のときだけ。**4xxは再送しない**（リクエスト自体が間違っているので、送り直しても結果は変わらない）
- 待ち時間は**指数バックオフ＋ジッター**（200ms → 400ms → 800ms…に揺らぎを加え、多数のクライアントが一斉に再送するのを避ける）
- **上限回数と全体の期限**を決めておく（デフォルト：最大4回、全体で10秒）
- 409 `request_in_progress` が返ったら、**同じキーで**再送する（新しいキーを作らない）

`retry_with` はジッター関数を注入できる形にしてあり、テストでは決定的なジッターとミリ秒単位の待ち時間で高速に検証しています。単体テストでは「再送可能なエラーでは成功まで再送する」「4xx相当では再送しない」「上限回数で止まる」を確認しています。

## 設計の代償・割り切り

- **処理中（processing）の扱い**：このサンプルは「待たせず 409 を返し、クライアントに同じキーで再送させる」方式です。サーバー側で待たせる方式もありますが、接続を長く占有します。処理が長引く場合は「202 Accepted + 状態確認API」の方が適します。
- **処理中のまま止まった場合**：実運用では、サーバーが処理中に落ちるとキーが `processing` のまま残ります。一定時間を超えた `processing` を失敗扱いにして再処理可能にする、といったタイムアウト設計が必要です（サンプルでは未実装）。
- **キーの保持期間**：キーを消すと「遅れて届いたリトライ」を新しい支払いとして処理してしまいます。本番では24時間程度保持し、期限切れをバッチで削除する想定で、DDLに `expires_at` を入れてあります。
- **リクエストハッシュの不一致**：同じキーで違う内容が来るのはクライアントのバグなので、黙って処理せず 422 で返します。ハッシュ対象に何を含めるか（金額・通貨など「支払いの意味を変えるもの」）は設計判断です。
- **インメモリ実装の限界**：単一プロセス・再起動で消える・スケールしない、は学習用サンプルの割り切りです。永続化する場合は `schema.postgres.sql` の形になります。
